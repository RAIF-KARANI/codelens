# CodeLens

AI code review assistant for GitHub pull requests, built on Graph RAG: it parses a
repository into a code graph (functions, classes, calls, imports), retrieves relevant
context with hybrid vector + full-text search plus graph expansion, and asks an LLM for
severity-graded review findings.

> **Status:** Phases 1–4 done: the indexer, the review pipeline, the eval harness and the
> measured upgrades ([`evals/RESULTS.md`](evals/RESULTS.md)). Phase 5 done: a GitHub App
> that reviews pull requests with inline comments, using local models, typically within a
> minute ([`docs/e2e.md`](docs/e2e.md)). Next: the dashboard. The plan of record is
> [`planning.md`](planning.md); how the system works today, component by component, is in
> [`architecture.md`](architecture.md).

## Repository layout

```
apps/web/            Next.js dashboard (Phase 6, in progress)
services/api/        FastAPI app            -> import name `api`
services/worker/     Celery background jobs -> import name `worker`
packages/core/       Shared Python library  -> import name `core`
evals/               Golden PR set + benchmarks (later)
```

The Python code is a single [uv workspace](https://docs.astral.sh/uv/concepts/projects/workspaces/):
one `uv.lock`, one virtualenv, three packages. `api` and `worker` both depend on `core`,
so models, DB access, and the parser are written once.

## Prerequisites

- Docker Desktop (with Compose v2.24+)
- [uv](https://docs.astral.sh/uv/getting-started/installation/) for running Python locally
- Node 22 + pnpm 9 for the dashboard

## Quick start

```bash
cp .env.example .env          # defaults work out of the box
docker compose up --build
```

This starts:

| Service    | URL / port              | Notes                                  |
|------------|-------------------------|----------------------------------------|
| `postgres` | `localhost:5433`        | Postgres 16 + pgvector                 |
| `redis`    | `localhost:6379`        | Celery broker + result backend         |
| `migrate`  | n/a                     | Runs `alembic upgrade head`, then exits |
| `api`      | http://localhost:8000   | `/health`, `/docs`; hot-reloads        |
| `worker`   | n/a                     | Celery, `index` queue (2 at a time) |
| `worker-gpu` | n/a                   | Celery, `gpu` queue: embedding and reviews, one at a time; `docker compose restart worker worker-gpu` after edits |

Check it:

```bash
curl http://localhost:8000/health
docker compose exec worker celery -A worker.celery_app call worker.ping
```

Postgres is published on host port **5433**, not 5432, so it doesn't collide with a
locally installed Postgres (inside the compose network it's still 5432). If 5433/6379/8000
is taken on your machine, change `POSTGRES_PORT` / `REDIS_PORT` / `API_PORT` in `.env`
(and the port in `DATABASE_URL` to match).

## Local Python development

```bash
uv sync                       # creates .venv with all packages + dev tools
uv run pytest                 # all tests (integration ones need postgres + redis up)
uv run pytest -m "not integration"   # unit tests only, no services needed
uv run ruff check . && uv run ruff format .
uv run pre-commit install     # once, after `git init`
```

Integration tests create and drop their own `codelens_test` database, so they never
touch your dev data.

Parser/indexer behaviour is pinned by golden files: `packages/core/tests/fixtures/repos/`
holds two small repos (`py_shop`, `ts_shop`), and each has a sibling `.graph` file
listing every file, node and edge. After an *intentional* change to extraction or
resolution, regenerate them and review the diff before committing:

```bash
UPDATE_GOLDEN=1 uv run pytest packages/core/tests/test_fixture_repos.py
```

## Database migrations

Models live in `packages/core/src/core/db/models/`; migrations in
`packages/core/src/core/db/migrations/versions/`. Compose applies them automatically
on `up`. By hand:

```bash
uv run alembic -c packages/core/alembic.ini upgrade head
uv run alembic -c packages/core/alembic.ini revision --autogenerate -m "describe change"
```

Always read an autogenerated migration before committing it. A test
(`test_models_match_migrations`) fails if models and migrations drift apart.

## Model providers (Ollama)

CodeLens uses local models through [Ollama](https://ollama.com), running natively on
the host so it can use the GPU (containers reach it at `host.docker.internal:11434`).

```bash
ollama pull qwen3:8b
ollama pull qwen3-embedding:0.6b
uv run python -m core.providers      # checks Ollama, models, embedding dim, structured output
```

Model names, context size and the Ollama URL are settings (see `.env.example`). Set
`LLM_PROVIDER=fake` / `EMBED_PROVIDER=fake` to run without any model (tests do).

## Indexing a repository

`core.index` parses a repo and writes its code graph to Postgres (using `DATABASE_URL`):

```bash
uv run python -m core.index path/to/repo                  # stored as "local/<dir name>"
uv run python -m core.index path/to/repo --name acme/app  # or under an explicit name
```

It prints files (new / changed / unchanged / deleted), nodes and edges by kind, and the
share of calls resolved. Re-running on an unchanged repo writes nothing to the graph
tables; changing one function rewrites only that function's row (and its file's edges),
so unchanged nodes keep their IDs and embeddings. Every run is recorded in `index_runs`.

Inside the stack: `docker compose exec worker python -m core.index /app/packages/core/src`.

## Embedding a repository

After indexing, embed the code nodes (needs Ollama; see above):

```bash
uv run python -m core.embed local/my-app            # the name core.index printed
uv run python -m core.embed local/my-app --limit 200 # try a few first
```

Only stale nodes are embedded: new ones, ones embedded by a different model, or ones
whose chunk text changed. A re-run on an up-to-date repo writes nothing. Each node's
chunk is its code plus a short header (path, symbol, enclosing class); classes and
modules are embedded as skeletons (members replaced by their signatures).

## Searching a repository

Once a repo is indexed and embedded, search it by meaning:

```bash
uv run python -m core.search local/my-app "retry a failed HTTP request"
uv run python -m core.search local/my-app "compute tax" --k 5 --kinds function,method
uv run python -m core.search local/my-app "compute tax" --explain   # show the Postgres plan
```

The query is embedded with the retrieval instruction and matched by cosine distance
(pgvector), scoped to that one repo.

## What a branch changed

See which functions and classes a branch touched, the starting points of a review:

```bash
uv run python -m core.changes path/to/repo --base main --head my-feature
```

It diffs head against its merge-base with base (like a GitHub PR), reading git objects
only (no checkout, no database), and attributes each changed line to the innermost
function/class/module: `+` added, `~` modified, `-` deleted.

## Reviewing a branch

End to end: index + embed the base, then review a branch against it.

```bash
uv run python -m core.index path/to/repo                 # at the base (e.g. main checked out)
uv run python -m core.embed local/repo
uv run python -m core.review path/to/repo --base main --head my-feature
uv run python -m core.review path/to/repo --base main --head my-feature     --config configs/pipeline/a0_diff_only.yaml            # the diff-only reference point
```

The review attributes changes to functions/classes, retrieves related code by meaning,
packs it into prompts that fit the model's context window, asks the LLM for structured
findings, and validates them (lines must be on changed code, evidence must have been
shown, confidence threshold, dedupe, cap). Everything is stored: `reviews`, `findings`
(posted *and* dropped, with the reason), `review_context_items` (what the model saw and
why), `review_events` (timeline). Pipeline knobs live in `configs/pipeline/*.yaml`.

On an 8 GB GPU, `LLM_NUM_CTX=8192` (the default) keeps the LLM entirely in VRAM. For a
16k window, set `OLLAMA_FLASH_ATTENTION=1` and `OLLAMA_KV_CACHE_TYPE=q8_0` for the Ollama
server first: measured on an RTX 4060, 16k then fits at full speed, while without them
it spills to CPU at half speed (numbers in `planning.md` §1.3; tools in `scripts/`).

## The API and background jobs

The API (`services/api`) is a thin HTTP layer. Real work runs in Celery workers
(`services/worker`), one per queue: `index` (parse and persist, 2 at a time) and `gpu`
(embedding and reviews, one at a time, so two jobs never compete for VRAM). The API
enqueues tasks by name (`core/jobs.py`) and returns `202` at once.

Every `/api/v1` route needs a bearer token (HS256, signed with `API_JWT_SECRET`, at least
32 bytes). With no secret set, the API refuses them all. Mint a development token with:

```bash
uv run python -m api.token --login me          # uses API_JWT_SECRET from .env
```

| Method | Path | What |
|---|---|---|
| GET | `/api/v1/repos`, `/api/v1/repos/{id}` | repos, with the latest index run |
| POST | `/api/v1/repos/{id}/index` | re-index, then embed what changed (`202`) |
| GET | `/api/v1/repos/{id}/index-runs`, `/api/v1/repos/{id}/reviews` | history, newest first (`?cursor=&limit=`; reviews also `?status=`) |
| POST | `/api/v1/reviews` | queue a review `{"repo_id", "base", "head"}` (`202 {review_id}`) |
| GET | `/api/v1/reviews/{id}` | a review and its findings (`?include_dropped=true` for the rejected ones) |
| GET | `/api/v1/reviews/{id}/events` | the review's progress as Server-Sent Events: replay after `Last-Event-ID`, then live, until `end` |
| GET | `/api/v1/reviews/{id}/diff`, `/trace`, `/graph` | what was reviewed, why each piece of context was used, and the call graph around the change |
| GET | `/api/v1/nodes/{id}` | a code node's source (a finding's evidence) |
| POST / DELETE | `/api/v1/findings/{id}/feedback` | 👍 / 👎 on a finding |

A token sees the repos of the GitHub App installations it lists (`--installation ID` on
`api.token`); logins in `API_ADMIN_LOGINS` see every repo, including local ones.

Errors always have the shape `{"error": {"code", "message", "details"}}`. With
`DEMO_MODE=true`, every mutating route returns `403`.

Until the GitHub App lands, re-indexing and manual reviews work on repos indexed from a
local checkout (`core.index`). The API and the worker must both read that path, so run them
on the host, with Postgres and Redis from compose:

```bash
docker compose up -d postgres redis
uv run uvicorn api.main:app --port 8000
uv run celery -A worker.celery_app worker -Q index,gpu --pool=solo   # --pool=solo on Windows
```

```bash
curl -X POST localhost:8000/api/v1/reviews -H "Authorization: Bearer $TOKEN" \
     -H "Content-Type: application/json" -d '{"repo_id": 1, "base": "main", "head": "my-feature"}'
curl localhost:8000/api/v1/reviews/1 -H "Authorization: Bearer $TOKEN"
```

## The GitHub App

CodeLens reaches GitHub as a GitHub App, created from a manifest in this repo with one
command, and receives its webhooks at `POST /webhooks/github` (signature-checked,
deduplicated). Installed on a repo, it mirrors and indexes the repo, re-indexes on pushes
to the default branch, and reviews every pull request push, posting one comment review
with inline findings. Setup, including the local webhook tunnel and a connection check, is in
[`docs/github-app.md`](docs/github-app.md):

```bash
uv run python -m core.github register --name "CodeLens (you)" --webhook-url https://smee.io/<channel>
uv run python -m core.github check
```

Running the whole system end to end (Docker, the App, the webhook relay, watching a review
live) is in [`docs/e2e.md`](docs/e2e.md).

## Parser (inspect the code graph)

`core.parser` turns a repo into nodes (modules, classes, functions, methods) and edges
(calls, imports, inherits, contains), with no database involved. The debug CLI shows
what it sees:

```bash
uv run python -m core.parser path/to/repo                 # summary + % calls resolved
uv run python -m core.parser path/to/repo --nodes --file src/app.py
uv run python -m core.parser path/to/repo --unresolved    # in-repo calls it couldn't resolve
```

## Dashboard

A Next.js app that signs you in with GitHub (through the App's OAuth client) and reads
the API from its server. So far it has the login and the repos page; the review pages
come in the next Phase 6 steps. It needs the API running, `apps/web/.env.local` (copy
`apps/web/.env.example`), and the App's callback URL set
([`docs/github-app.md`](docs/github-app.md) §5).

```bash
cd apps/web
pnpm install
pnpm dev                      # http://localhost:3000
pnpm test                     # vitest
pnpm lint && pnpm build
```

## Configuration

All config comes from environment variables, parsed by `core.config.Settings`
(pydantic-settings). See `.env.example` for the full list. Notable:

- `EMBED_DIM`: embedding vector size. It is fixed into the database schema when the
  migration runs, so pick it to match your embedding model before the first migration.
